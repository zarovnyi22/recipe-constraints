# Recipe Constraints — чому так

**Модель розуміє, розв'язувач рахує, незалежний код перевіряє.** LLM погано рахує і
вигадує правдоподібні цифри; LP-розв'язувач гарантує, що рецептура задовольняє лінійні
обмеження, або доводить, що такої немає. Але розв'язувач перевіряє лише те, що ми в нього
поклали, тому окремий перевіряльник з іншого коду перераховує все з грамів — це і є доказ
для технолога і для PM.

**Чому LP, а не перебір чи LLM.** Усі вимоги технолога (нутрієнти на 100 г, частка енергії
білка, ціна, цукровий еквівалент, дози) лінійні за грамами. HiGHS у scipy безкоштовний,
детермінований і дає сертифікат нездійсненності; еластичний LP — природна відповідь на
«що послабити».

**Чому «звичайний» = еталон з даних.** «Не менше, ніж у звичайного» і «зі зниженим
вмістом» без еталона безглузді; модель не має права придумати цифру еталона.

**Чому технологія — жорсткі обмеження.** Без шаблону розв'язувач видасть «йогурт» з води й
білкового порошку. Шаблон (основа, закваска, межі доз, характерний інгредієнт) — це знання
технолога, яке не послаблюється автоматично.

**Невідомі запити PM.** Найгірше — тихо проігнорувати частину запиту або вигадати
категорію. Тому кожна фраза — обмеження, `unparsed` або `unsupported`; статус `partial`
чесно каже, що враховано не все.

**Уроки попередніх проєктів:** незалежне рев'ю знаходило «pass на порушенні»;
test пише той, хто не бачив налаштувань; кеш LLM у git для відтворення; один фінальний
замір на test.

Чим жертвуємо: лише 6–9 категорій; нутрієнти й ціни — типові значення/оцінки; без
технологічних властивостей поза межами доз (в'язкість, pH, стабільність не моделюються);
без втрат при термообробці, крім фіксованого коефіцієнта для печива.

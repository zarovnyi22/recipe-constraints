# Нотатки між кроками

## Дані (B1b)
- Конвенція: `carbs` = засвоювані БЕЗ клітковини і поліолів (ЄС); `polyols` — «інші» вуглеводи з
  енергією ≠ 4 (еритрит, мальтитол, лимонна/оцтова кислота). Atwater: low = 4P+9F+4C, high = low +
  2·fibre + 2.4·polyols, допуск ±15 % (+2 ккал). `app.data.energy_bounds` — спільна функція;
  verify.py (B3a) має писати свою незалежну версію.
- `sweetness` — сахарозний еквівалент на 1 г інгредієнта; `sweetness_min` шаблону — г-екв на 100 г
  ГОТОВОГО продукту = Σ(x·sweet)/10.
- Ролі шаблону: `one_of` (yogurt: base і culture) — розв'язувач перебирає варіанти (7×3 LP), `blend` —
  звичайна суміш. Інгредієнт має `min_dose_pct`, якщо він використаний (закваски: DVS 0,01–0,05 %,
  виробнича 1–3 %); `dose_limits_pct` шаблону суворіші за інгредієнт (еритрит ≤ 8 % у м'яких).
- `flavor_min_pct` ролі fruit (йогурти): якщо просять смак — мінімум ролі; без смаку fruit може бути 0.
- Печиво: `moisture_loss_pct` 10 → маса сирої рецептури = 1000/(1−0,10) = 1111,1 г, відсотки ролей — від
  неї; нутрієнти на 100 г готового = Σ(x·n)/1000; ціна/кг готового = Σ(x·price)/1000 (партія = рівно 1 кг).
- Ціни — оцінки; опори з посиланнями в `PRICES.md` лише для цукру, молока-сировини, олії (борошно — частково, полуниця IQF — не знайдено). Після правок базова рецептура йогурта коштує 44,0 грн/кг (було 47,3).
- `glucose_syrup`: DE 40, цукри 40 г/100 г (Atwater сходиться). Мед, WPC80, ізоляти — верхня межа цін. Еталони — типові значення, не вимірена вибірка.
- `date_paste` має `added_sugar: true` (підсолоджувач/зв'язка), сухофрукти-ціле (родзинки) — ні.
- Алергени: `plant_margarine` = soybeans (лецитин, консервативно); `spice_blend` may_contain celery, mustard.

## Розгортання (B2a)
- `expand(spec, data) → Expansion`: `variables` (усі інгредієнти ролей шаблону), `constraints`
  (LinearConstraint, op `<=`/`>=`, `==` лише для маси), `one_of` {роль: кандидати} — розв'язувач
  перебирає, `min_dose_g` — напівнеперервні мінімуми (якщо використано) для B2b.
- Масштаб коефіцієнтів: ліва частина в одиницях `unit` (г/100 г = Σx·n/1000; грн/кг = Σx·ціна/1000;
  % рецептури = 100·x/batch_mass_g), тож `rhs` — людське число для «послабити з 45 до 52».
- `group` — одна вимога → кілька рядків (reduced_sugars: цукри + енергія; `==` → смуга ±2 %;
  satfat_low: грами з запасом 0,1 г + ≤10 % енергії). Послаблювати/показувати — по `group`.
- Виключення (алергени, дієти, інгредієнти, no_added_sugar, без підсолоджувачів) — рядок
  Σx ≤ 0, змінні НЕ видаляються. Алергени й дієти: `auto_relax: false` (лише «інший варіант»).
- Характерний інгредієнт (flavor) — жорстко: ≥ flavor_min_pct ролі і ≥ кожного іншого інгредієнта
  ролі. Без flavor_min_pct і з min_pct ролі 0 → unsupported. must_include без % → max(5 %,
  мінімум ролі / flavor_min_pct), обрізано дозволеним шаблоном (role max, Σ max доз) — запис в
  assumptions, статус не partial; unsupported лише якщо інгредієнта немає в базі або в шаблоні.
- Підсолоджувач = group sweeteners, не added_sugar, sweetness ≥ 0,1 — за Регл. 1333/2008
  (додаток I, «підсолоджувачі»): еритрит E968, стевіол-глікозиди E960, мальтит E965 — так;
  полідекстроза E1200 — ні (наповнювач); мед, фінікова паста — додані цукри, не підсолоджувачі.
- fibre_* — АБО: ≥ 3/6 г на 100 г, АБО ≥ 1,5/3 г на 100 ккал (рядки з `alt`, `either_or`
  {group: [per_100g, per_100kcal]}; розв'язувач перебирає альтернативи, як one_of).
- Напої: пороги для рідин (на 100 мл) → на 100 г як поріг ÷ `density_g_per_ml` шаблону (fix після RR1).
- Нічого не губиться: виключення, якого в шаблоні немає, і інгредієнт, якого немає в базі, —
  рядок в `assumptions` (виконано автоматично).

## Розв'язувач (B2b)
- `solve(exp, data) → Recipe | Infeasible`; `best_recipe` — найдешевша округлена рецептура по всіх
  варіантах (one_of × either_or; йогурт 21 LP), `explain` — конфлікт, послаблення, альтернативи.
- Округлення: 0,1 г, **нижче 1 г — 0,01 г** (стевія 0,04 г давала 0,9 г сах. екв./100 г; при 0,1 г
  вона зникала і ламала sweetness_min — відхилення від «0,1 г» SPEC свідоме). Цілі соті грама,
  різниця — у найбільший інгредієнт ролі base (без base — найбільший загалом), Σ = маса рівно
  (1000,00; печиво 1111,10). Перевірка всіх рядків варіанта; не тримається → LP з запасом ε 0,5 %,
  потім 2 % (`margin_pct` у Recipe). Juice/cookie/ketchup базові вже йдуть через ε 0,5 %.
- `LinearConstraint.relax`: `value` (нове число, «до 3 значущих» назовні) або `drop` (твердження,
  виключення — цілком). Еластичний LP: вага 1/|rhs| (1 для rhs 0), drop ×10.
- Порядок explain: шаблон без м'яких нездійсненний → `template_infeasible` (500); конфлікт —
  deletion filter по групах; спільне послаблення — спершу лише групи конфлікту, потім усі;
  альтернативи — кожна група окремо; `auto_relax: false` (алергени, дієти) → лише `other_options`
  з попередженням. Кожна зміна — через `_verify` (повний розв'язок з округленням; число не
  тримається → до 3 кроків назовні; ні → не пропонується).
- Рядок з `alt`, якого немає в `either_or`, → `solver_error` (інакше тихо зник би).
- min_dose поза one_of → `solver_error` (потрібен MILP; у даних немає).
- **Приклад з умови** (полуничний йогурт без молока, білок ≥ еталону 3,2, ≤ 45 грн/кг,
  reduced_sugars): нездійсненний. Конфлікт: {собівартість ≤ 45, без молока}. Послаблення:
  собівартість → 52,9 грн/кг (рецептура 52,84: соєвий напій 805,3, полуниця 100, цукор 85,8,
  ізолят сої 8,8, DVS рослинна 0,1). Інший варіант (з попередженням): з молоком — 36,03 грн/кг.
  Без «без молока» здійсненний: білок і reduced_sugars — щільні, стевія 0,04 г.
- **Закваска ↔ основа** (fix після B2b): `pairings` шаблону (жорстко) — рослинна основа → лише
  `dvs_culture_plant`, молочна → `bulk_starter_milk`/`dvs_culture_dairy` (за `group` основи).
  `Expansion.forbidden_pairs` — пари one_of, які розв'язувач не перебирає; verify (B3a) має
  перевіряти це сам з шаблону. «Соєвий йогурт» без «без молока» тепер без milk.
- Інгредієнт/смак є в базі, але не в шаблоні → unsupported «є в базі, але шаблон X його не передбачає».
- Базові шаблони без вимог дають мінімалістичні рецептури (печиво без яєць) — жорстких мінімумів
  ролей мало.

## Перевірка і /formulate/structured (B3a)
- `verify(grams, spec, data, reported_cost, relaxed) → (checks, totals, lines)`: з грамів і YAML,
  без рядків розв'язувача; спільні лише пошук (find_template, match_ingredients) і юридичні пороги
  (`app.claims`). Id soft-перевірок = group з expand (`cost_max`, `nutrient:0:protein`,
  `claim:…`, `allergen:0:milk`, `must_include:0:…`) — так послаблення мапиться на перевірку.
  Hard: template, mass, grams (крок 0,01), role:*, one_of:*, dose:*, sweetness_min,
  pairing:base:culture, flavor, cost_reported; у formulate — `coverage` (кожна фраза spec має
  перевірку або unsupported).
- Алергени в verify = allergens ∪ may_contain ∪ словник label-check по name_uk/aliases
  (`app/allergens.py`; додано «без X» маскує X і «мигдалев-»). Тест тримає словник ≡ дані.
- `relaxed_recipe`: розв'язувач повертає рецептуру спільного послаблення (`Infeasible.relaxed_recipe`);
  verify з `relaxed=relaxations` — нове число (`relaxed` = мітка), `drop` → `enforced: false`.
  Приклад з умови: 52,84 грн/кг, усі 24 перевірки pass, cost_max «≤ 52.9 (послаблено)».
- Будь-яка enforced-перевірка fail (і в relaxed_recipe) → run зі status `error` у БД (рецептура
  для аудиту), відповідь 500 `verification_failed` з id/вимогою/фактом; GET не віддає рецептуру.
- (fix) `runs.response` (міграція 002) — уся відповідь; GET віддає її (run_id = id рядка; для
  status error рецептури приховано). Інші стовпці — частини для SQL. Запуски до 002 → 404.
- (fix) solver_error / template_infeasible / rounding_failed і непередбачений виняток теж пишуться
  в runs зі status error (виняток потім прокидається → 500 internal_error).
- (fix) Покриття — за id вимоги (`schemas.requirement_ids` = group expand = id перевірки verify),
  `Unsupported.id`; дві вимоги з однієї фрази потребують двох перевірок. `sweeteners.allowed: true`
  — дозвіл: рядок у assumptions, перевірки не потребує (раніше покриття за фразою його б завалило).
- `run_formulate(spec, pool=None)` — без БД для eval (run_id None); `solve_fn` для FakeSolver.

## Розбір LLM (B3b)
- `app/llm/` — копія з `pet` (base/gemini/groq/fallback/fake); `LLMClient.model`/`models`, модель у
  `FormulateOut.model` = `provider:model` того, хто відповів. `PROMPT_VERSION = p1`; промпт будується
  з data/ (шаблони, інгредієнти, твердження). Ключ кешу: текст + версія промпту + модель + data_version.
- Схема (рішення в межах кроку): `ConstraintSpec.unsupported` (фраза + причина від моделі; разом з
  unsupported розгортання → статус `partial`) і `optimize_phrase` («якомога дешевше» — запис у
  assumptions, не втрата). Категорії немає/не названо → `product.template` = як у тексті або
  «(не названо)», далі `expand` дає unsupported з переліком.
- Код після моделі (`validate_spec`): вигадана цитата → вимога відкинута, в `unparsed` «цитати немає в
  запиті»; число вимоги (value, cost, min_pct) мусить бути в її фразі; кратність до еталона ≠ 1 →
  unsupported; непокриті слова запиту (крім службових; «без», «до» службовими НЕ є) → unparsed.
  Невалідний JSON/spec → один повтор з текстом помилки, далі 502 `llm_bad_output`.
- Живі виклики (5 з 10, gemini-3.5-flash-lite): умова → інфізібл з тим самим конфліктом, що й
  structured; веганський батончик з горіхами + білок ≥ 10 → feasible 48,9 грн/кг; «яблучний сік без
  доданого цукру» → unsupported (шаблон лише «соковмісний напій», 100 % сік не підтримується; чи
  мапити «сік» на juice_drink — рішення для B5/README); печиво з низькою ціною без пальмової олії →
  partial (пальмової олії немає в базі → «гарантувати не можемо», «низька ціна» → optimize_phrase);
  «пиріг з нутелою» → unsupported з переліком категорій. Фраз не загублено ні в одному.

## Раннер, метрики, proof (B4b)
- `eval/run.py`: кеш — сира відповідь моделі `eval/cache/<split>/<id>.json` (ключ: sha тексту + sha системного промпту [+ модель при --live]); після кешу `spec_from_raw` (validate_spec) і весь код далі — на поточному коді. Без `--live` нема кешу → `NotCachedError` з переліком. DB `parse_cache` лише з `--live`. Помилка розбору/сервісу — рядок `error`, не падіння.
- `eval/metrics.py`: відповідність (checks, `verification_failed` рахується як провал), статус + confusion, розбір (precision/recall ключових обмежень; вільні слова — за основами слів), названі unsupported/unparsed, конфлікти, послаблення (`verified` + relaxed_recipe checks; **eval не розв'язує повторно сам**), нічого не загублено, `satisfies_expected` — рецептура проти файлу запиту (не проти spec моделі; claims і vegetarian не перевіряє).
- `make proof [SPLIT=test]` → `docs/proof.md` (dev → `docs/proof_dev.md`) з останнього `eval/reports/<split>_<date>.json`. Звіти й proof_dev не коміщу, поки замір неповний.
- Дрібниця B4a: «без лактози» → запис в assumptions (expand).

## Незалежна перевірка послаблень (B5, перед заміром)
- `eval/relax_check.py`: кожна пропозиція (спільне послаблення — одна, кожна альтернатива й «інший
  варіант» — окремо) записується назад у spec (`apply_changes`: cost_max/nutrient/must_include — нове
  число; відносний нутрієнт стає абсолютним; «==» — смуга ≥/≤ з незміненим краєм; drop — вимогу
  прибрано) і йде через `run_formulate` + verify. `row["relax_check"]` у звіті; метрика «послаблення»
  рахує лише їх, `verified` сервісу не враховує. Рядок без re-check або зміна, яку не вміємо
  застосувати (`CannotApply`), — провал, не пропуск.

## C1: не більше 6 інгредієнтів (коміт «feat(c1): max 6 ingredients»)
- `data.MAX_INGREDIENTS = 6`; `Ingredient.supplier` (false лише у води: з водопідготовки). Валідація: базові
  рецептури ≤ 6 (батончик був 8 — прибрано родзинки й олію, пластівці 387 → 527).
- `expand(spec, data, max_ingredients=6)` → `Expansion.max_ingredients`, `uncounted`. Розв'язувач: у `_lp`, якщо
  відкритих (не закритих варіантом one_of) лічених змінних більше за ліміт, — `scipy.optimize.milp`: x ≤ M·y,
  M = маса партії, Σy ≤ ліміт (і для elastic/feasibility/repair — та сама модель, тож послаблення й
  relaxed_recipe теж ≤ 6). Інакше — linprog, як було. `MILP_SECONDS = 20` — перевищення = solver_error.
- explain: шаблон без м'яких вимог нездійсненний лише через ліміт → conflict []. `limit_hit` — ядро конфлікту
  здійсненне без ліміту → ConflictItem `max_ingredients` («правило: не більше 6 інгредієнтів …»), `explanation`,

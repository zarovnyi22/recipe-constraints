# Recipe Constraints

Технолог пише словами, який продукт хоче («полуничний йогурт без молока, білка не менше, ніж у
звичайного, собівартість до 45 грн/кг, і щоб можна було написати "зі зниженим вмістом цукру"»).
Сервіс повертає **рецептуру в грамах на 1 кг готового продукту** або чесно пояснює, чому такої немає
і що саме послабити. Ринок — Україна, тексти українською; твердження — Наказ МОЗ № 1145
(= додаток Регл. 1924/2006).

## Архітектура: модель розуміє, розв'язувач рахує, незалежний код перевіряє

```
текст запиту → LLM (Gemini; запасний Groq): ЛИШЕ структурування в ConstraintSpec
               з цитатою фрази-джерела + unparsed[] (що не зрозуміла)
            → код: валідація (вигадана цитата чи число → відкинуто), розгортання: шаблон продукту,
               еталон, твердження, алергени → лінійні обмеження
            → LP-розв'язувач (scipy HiGHS): мінімум собівартості, Σ = 1000 г
            → є рішення: округлення до 0,1 г → рецептура
              немає: еластичний LP → конфлікт + «що послабити» (кожна пропозиція перевірена
              повторним розв'язком)
            → НЕЗАЛЕЖНИЙ перевіряльник (app/verify.py: рахує з грамів і YAML, не з матриць
               розв'язувача): нутрієнти, ціна, алергени, твердження, дози, шаблон → checks[]
            → PostgreSQL: запит, spec, рецептура, checks, модель, версії (аудит)
```

Модель не рахує і не вигадує цифр: грами, нутрієнти, ціни, пороги — лише код і дані. **Рецептура
віддається, лише якщо незалежна перевірка пройшла всі checks**; інакше — помилка
`verification_failed` (це баг, а не відповідь). Жодна фраза запиту не губиться мовчки: вона —
обмеження, `unparsed` (не зрозуміла) або `unsupported` (зрозуміла, але не підтримуємо); з такими
фразами статус ніколи не `feasible`, а `partial`.

Стек: Python 3.12, FastAPI, Pydantic v2, PostgreSQL 16 (asyncpg, SQL-міграції), scipy (HiGHS),
httpx, Docker Compose, pytest, ruff, GitHub Actions. Фронтенду немає — Swagger UI.

## Запуск за 3 команди

На хості потрібен лише Docker (Compose v2).

```bash
cp .env.example .env      # вписати GEMINI_API_KEY (Google AI Studio, free tier, без картки)
make up                   # db + api: http://localhost:8020 (Swagger UI: /docs)
make health               # {"status":"ok","db":"ok","llm_provider":"gemini",...}
```

Ключ потрібен лише для `POST /formulate` (розбір тексту). Усе інше — `/formulate/structured`,
`make test`, відтворення eval з кешу — працює без ключа й без мережі. Запасний провайдер: Groq
(`GROQ_API_KEY`, `LLM_FALLBACK_PROVIDER=groq`, модель `openai/gpt-oss-120b`). Порти: api `8020`,
db `127.0.0.1:5434`. `make down` зупиняє стек (дані лишаються в томі `pgdata`).

Тести (ruff + pytest, 280 тестів, ізольована мережа без інтернету й ключів, окрема БД `recipe_test`):

```bash
make test
```

## Як перевірити своїм запитом

```bash
scripts/ask.sh "полуничний йогурт без молока, білка не менше, ніж у звичайного, до 45 грн/кг, зі зниженим вмістом цукру"
make ask Q="злаковий батончик з фундуком і какао, без арахісу, до 120 грн/кг"
scripts/ask.sh --json "пиріг з нутелою"        # сира JSON-відповідь
```

Потребує `make up` і `GEMINI_API_KEY` у `.env`. Скрипт робить `POST /formulate` і друкує: статус;
рецептуру таблицею (інгредієнт, роль, г, грн); собівартість грн/кг; нутрієнти на 100 г;
перевірки (✅/❌: вимоги технолога по рядку, правила технології шаблону — лічильником);
`unsupported` / `unparsed` з причинами; для нездійсненного — конфлікт, мінімальні послаблення,
«інший варіант» з попередженням і `relaxed_recipe` (рецептуру для послабленої вимоги з її
перевірками). Усі числа беруться з відповіді API, форматувальник (`app/pretty.py`) нічого не
перераховує. Кожен запит лишається в БД (`run_id` у виводі, `GET /formulate/{id}`).

Приклад вивіду (скорочено) — запит з умови, який **нездійсненний**:

```
Статус: ❌ infeasible — за цих вимог рецептури немає (див. «Конфлікт» і «Що послабити»)
Конфлікт (ці вимоги разом неможливі):
  • собівартість не більше 45 грн/кг  («собівартість до 45 грн/кг»)
  • без алергену milk: виключено Молоко пастеризоване 2,5 %, … («без молока»)
Що послабити разом (мінімально, перевірено повторним розв'язком):
  • послабити: собівартість не більше 45 грн/кг → 52,9 грн/кг → рецептура 52.84 грн/кг
Інший варіант (не автоматично):
  • відмовитись від вимоги: без алергену milk … → рецептура 36.03 грн/кг
    ⚠️  вимогу щодо алергену/дієти не послаблюємо автоматично: рецептура міститиме виключене …
Рецептура зі спільним послабленням (relaxed_recipe):
  Соєвий напій 805.3 г, Полуниця 100 г, Цукор 85.8 г, Ізолят соєвого білка 8.8 г, Закваска DVS
  «без молочного» 0.1 г → 52.84 грн/кг; білок 3.2 г/100 г (еталон 3.2), цукри 9.45 ≤ 9.45
```

## API

- `POST /formulate` — `{"request": "<текст>"}` → розбір LLM + рецептура.
- `POST /formulate/structured` — `{"spec": ConstraintSpec}` → те саме без LLM (для тестів, eval, демо;
  у Swagger є готові приклади).
- `GET /formulate/{id}` — збережена відповідь; `GET /ingredients`, `GET /templates` (з собівартістю
  базової рецептури й еталоном), `GET /health`.
- Помилки — `{"error": {"code": "...", "message": "..."}}`: `llm_bad_output` (502), LLM недоступний /
  не налаштований / ліміт (503), `verification_failed`, `solver_error`, `template_infeasible` (500).

`FormulateOut`: `status` (`feasible` | `partial` | `infeasible` | `unsupported`), `recipe`, `totals`
(`cost_uah_per_kg`, `per_100g`), `checks[]` (`id`, `kind` hard/soft, `requested`, `actual`, `pass`,
`source_phrase`), `parsed` (spec, який зрозуміла модель), `unparsed`, `unsupported`, `conflicts`,
`relaxations`, `alternatives`, `other_options`, `relaxed_recipe`, `contradictions`, `assumptions`.
Деталі — `docs/SPEC.md` §1.

**Приклад 1. Здійсненний** (той самий запит з молоком, 36,03 грн/кг; `make ask`):
молоко 2,5 % 831,06 г, полуниця 100 г, цукор 50,4 г, закваска 10 г, ізолят сої 8,5 г, стевія 0,04 г;
білок 3,2 г/100 г (еталон 3,2), цукри 9,45 г (= 0,7 × еталон 13,5), усі 23 правила шаблону пройшли.

**Приклад 2. Нездійсненний** — див. вище: сервіс називає мінімальний конфлікт і дає число, до якого
послабити (52,9 грн/кг), а не «неможливо». Алерген-виключення сервіс **не послаблює сам**: лише
пропонує як «інший варіант» з попередженням.

**Приклад 3. Unsupported:** «пиріг з нутелою» → `status: unsupported`: у `unsupported` — «пиріг» з
переліком 8 підтримуваних категорій, а «з нутелою» — «категорія не підтримується, тож вимогу не
розглядали». Якщо категорія підтримується, але частину фрази сервіс не зміг перенести в обмеження
(«щільна текстура»), вона лишається видимою в `unparsed` / `unsupported`, а статус — `partial`,
не `feasible`.

## Доказ відповідності

**Що доводить:** кожна рецептура, яку сервіс віддав, пройшла незалежну перевірку
(`app/verify.py`) — нутрієнти, ціна, алергени (з «може містити»), твердження, дози, шаблон,
закваска ↔ основа, водний баланс печива. Перевіряльник не використовує матриць розв'язувача; спільні
з ним лише пошук інгредієнтів/шаблону й юридичні пороги (`app/claims.py`), які покриті окремими
тестами. Збій перевірки — це `verification_failed`, а не відповідь.

**Три способи подивитись на ті самі 20 test-запитів** (субагент бачив лише умову таски; фінальний замір
зроблено один раз, живим Gemini, після нього нічого не налаштовувалось). Різниця між колонками — не в
моделі (її відповіді закомічені в `eval/cache/` і однакові), а в коді й даних, на яких їх обробляють:

| метрика | 1. Фінальний замір — **чесне число** | 2. Після фіксів B5b (для інформації) | 3. Поточний код |
|---|---|---|---|
| рецептури, що пройшли незалежну перевірку (мета 100 %) | **15 з 15** | 15 з 15 | 15 з 15 |
| відповідають файлу запиту (ціна, нутрієнти, алергени, інгредієнти) | 8 з 10 | 8 з 9 | 9 з 9 |
| статус збігається з очікуваним | **16 з 20** | 18 з 20 | 18 з 20 |
| розбір: recall / precision ключових обмежень | 50 з 52 / 52 з 57 | те саме | те саме |
| названо очікувані unsupported/unparsed (у правильному списку) | 6 з 6 (5 з 6) | те саме | те саме |
| конфлікти: recall / precision | 3 з 7 / 3 з 5 | 5 з 9 / 5 з 7 | 5 з 9 / 5 з 7 |
| послаблення, що при повторному розв'язку в eval дають рецептуру з усіма checks pass | 8 з 8 | 11 з 11 | 11 з 11 |
| рецептури рекомендованих послаблень пройшли перевірку | 5 з 5 | 6 з 6 | 6 з 6 |
| нічого не загублено | 20 з 20 | 20 з 20 | 20 з 20 |
| `feasible` з нерозпізнаними/непідтриманими фразами (мета 0) | 0 | 0 | 0 |
| код і дані | коміт `3ff5701` (тег `final-test-eval`), дані `8d3b0e3009d0` | коміт `78c4bcb`, дані `ff27327e1369` | `main`, дані — поточні |
| звіт | [`docs/proof.md`](docs/proof.md) | [`docs/proof_after_fixes.md`](docs/proof_after_fixes.md) | [`docs/proof_head.md`](docs/proof_head.md) |
| **команда** (чистий клон, без ключа й мережі) | `git checkout final-test-eval && make eval SPLIT=test && make proof` | `git checkout 78c4bcb && make eval-after-fixes` | `git checkout main && make eval SPLIT=test` |

Звіт кожної колонки відтворюється слово в слово; єдина різниця в 1-й — шапка «живий розбір» → «розбір з
кешу». Вибірка мала (20 запитів, 15 рецептур), 95 % інтервали Вілсона широкі (напр. відповідність
80–100 %) — вони є в звітах. «Відповідність 100 %» — не гарантія на будь-який запит, а результат: на
15 з 15 перевірка не знайшла розбіжностей, а шляхи її обходу шукало окреме глибоке рев'ю
(`docs/reviews/RR1.md`; знахідки закриті регресійними тестами в `tests/test_rr1.py`). **Чесне число —
колонка 1**; колонки 2 і 3 показують, що дали виправлення й нові дані після заміру.

Dev-набір (17 запитів, на ньому налаштовували): `make eval SPLIT=dev` → `docs/proof_head_dev.md`
(статус 16 з 17, розбір 28 з 28 / 28 з 29, конфлікти 7 з 7, послаблення 12 з 12).

**Де сервіс помилявся** (колонка 1): конфлікти — розв'язувач називає ОДИН мінімальний конфлікт
(deletion filter), а очікування в test часто перелічує ширший (t06, t08, t09, t11); статус — «Протеїновий
батончик» модель позначила `unsupported` (LLM надобережна), «вівсяне печиво» упиралось у відсутність
вівсяних пластівців у шаблоні печива, «мигдаль і фундук, але без горіхів» давало `partial` замість
`infeasible`; два кейси не відповідали файлу запиту, бо інгредієнтів (фундук, шпинат) не було в базі —
сервіс чесно вніс їх у `unsupported`.

### Що змінилось після заміру (прозорість)

1. **B5b** (колонка 2) — виправлення за розбором помилок test: суперечність запиту («з мигдалем, без
   горіхів» називається явно), вівсяні пластівці й горіхи в шаблоні печива.
2. **Типові інгредієнти** (колонка 3, після заміру): +15 інгредієнтів, серед них **фундук і шпинат** —
   саме їх бракувало t10 і t12. Це доповнення бази на прохання замовника, але воно збігається з тим,
   що test «показав», тож колонка 3 не є чесним виміром. Зведені числа змінились лише в одному рядку
   («відповідає файлу запиту» 9 з 9 замість 8 з 9), проте **рецептури трьох запитів інші**: два
   батончики (в одному «джерело білка») беруть 10 % насіння льону замість ізоляту/кріспсів
   (колонка 2 → 3: 52,39 → 50,38 і 80,83 → 78,58 грн/кг), а смузі «зі шпинату і яблука» (t12) тепер
   справді містить 5 % шпинату (22,81 → 25,16 грн/кг). Усі вони проходять перевірку.

### Інше

- `make test` — 280 тестів, FakeLLM, без мережі й ключів.
- `make eval SPLIT=test` на `main` не викликає модель: це режим `--head` (кеш приймається і за зміненого
  системного промпта — він містить ролі шаблонів та інгредієнти з `data/`). Строго за промптом працює
  лише старий `make eval` на коміті заміру (колонка 1). Перегнати розбір заново —
  `make eval-live SPLIT=test` (потрібен ключ; це нове вимірювання, а не відтворення).
- Числа в прикладах вище (52,9 грн/кг, 36,03 тощо) — з `POST /formulate/structured` на прикладі «task»
  зі Swagger (без ключа) і з тестів `tests/test_solver.py`, `tests/test_formulate.py`.

## Припущення

(Питань до замовника не було: усе, що виглядало як розвилка, вирішено так і записано тут.)

1. **Ринок — Україна.** Тексти українською. Порівняльні твердження («зі зниженим вмістом…») —
   ≥ 30 % менше за еталон (для солі 25 %), для цукрів ще й енергія ≤ еталону; «високий вміст білка»
   тощо — пороги Наказу МОЗ № 1145 (`app/claims.py`). Для рідин пороги задано на 100 мл, рецептура
   рахує на 100 г: поріг ÷ густина шаблону (питний йогурт 1,03, напої 1,045, смузі 1,05 г/мл).
2. **«Звичайний» = еталон категорії** (`data/references.yaml`, з джерелом і поміткою «оцінка»):
   «білка не менше, ніж у звичайного» = білок ≥ еталона. Немає еталона — порівняльна вимога
   `unsupported`, цифр не вигадуємо.
3. **Рецептура на 1000 г готового продукту.** Термообробку не моделюємо; виняток — печиво: фіксована
   втрата вологи 10 % (маса сирої = 1111,1 г) з перевіркою водного балансу й вологості ≤ 10 %.
4. **Оптимізуємо собівартість** серед рецептур, що задовольняють усе. Округлення — до 0,1 г
   (нижче 1 г — до 0,01 г: стевія 0,04 г інакше зникає й ламає солодкість); Σ = маса рівно.
5. **Лише 8 категорій** (`data/templates.yaml`): йогурт густий, йогурт питний, соковмісний напій
   (сік ≥ 10 % — технологічне припущення), сік 100 %, смузі, батончик злаковий, печиво пісочне, кетчуп.
   Інша категорія → `unsupported` з переліком.
6. **Технологія — жорсткі обмеження** (основа продукту, межі доз, характерний інгредієнт, рослинна
   основа → лише рослинна закваска); вимоги технолога — м'які, саме їх пропонуємо послабити.
   Характерний інгредієнт («полуничний») — не менше ролі `flavor_min_pct` (йогурт 10 %) і не менше за
   інші в ролі. Вимога «з X» без відсотка = max(5 %, мінімум ролі), обрізано дозволеним шаблоном;
   запис у `assumptions`.
7. **Алергени:** «без X» виключає й те, що X містить (молоко → СЗМ, WPC, закваска, масло);
   «може містити» враховується як «містить». Цукровий «без цукру» / «без доданого цукру» — різні
   вимоги (мед, фінікова паста, глюкозний сироп — додані цукри). Підсолоджувач — група sweeteners
   без доданого цукру (еритрит, стевія, мальтит; полідекстроза — ні). Алерген і дієта не
   послаблюються автоматично.
8. **Дані — оцінки.** Нутрієнти — USDA FDC і корпус `pet` у конвенції ЄС (вуглеводи без клітковини,
   перевірка діапазону Atwater при завантаженні). «Ваніль» = ванільний ароматизатор (ванілін), не
   стручки. Желатин — не веган. Насіння (чіа, льон, кунжут) є у смузі, батончику й печиві, але
   **не в густому йогурті**: набухає, змінює текстуру, а льон за 70 грн/кг ставав дешевим джерелом
   білка. Межі доз солі/соди, що не дають «дешево заповнити» рецептуру, — типові (RR1).
9. **LLM:** Gemini (free tier), запасний Groq `openai/gpt-oss-120b`. Модель лише структурує; код
   відкидає вимоги з вигаданою цитатою чи числом, якого немає у фразі, а непокриті слова запиту
   перетворює на `unparsed` («без» і «до» службовими не вважаємо).
10. **Фронтенду немає** — Swagger UI, `scripts/ask.sh`.

## Джерела цін

Усі ціни в `data/ingredients.yaml` — **оцінки в грн/кг на жовтень 2026, не котирування**; для
кожного є `price_source` і `price_date`. Докладно — [`data/PRICES.md`](data/PRICES.md): три
підтверджені опори з відкритих джерел (цукор: оптова ціна виробників 21,32 грн/кг, червень 2026;
молоко-сировина 16 грн/кг, грудень 2025; соняшникова олія ≈ 108 грн/кг, Держстат, серпень 2026),
борошно підтверджено частково, ціну замороженої полуниці знайти не вдалося (свіжа ≈ 160 грн/кг у
сезон). Решта — оцінка відносно опор і загальних знань про ринок UA, без перевірки живими прайсами;
у `PRICES.md` позначено, які ціни — верхня межа (мед, WPC80, ізоляти, мигдаль, фундук, чіа).
Рецептура залежить передусім від **співвідношення** цін; для реального використання ціни замінюють
прайсами постачальників — сервіс бере їх тільки з YAML. «Собівартість до N грн/кг» у відповіді —
оцінка за цими цінами, а не фабрична калькуляція.

## Рішення і компроміси

- **LP, а не перебір чи LLM.** Усі вимоги лінійні за грамами; HiGHS детермінований і дає
  сертифікат нездійсненності, еластичний LP — природна відповідь на «що послабити». Ціна:
  вибір «один з» (основа, закваска) перебирається окремими LP, а напівнеперервні мінімуми доз
  (MILP) не підтримуються — у даних їх немає.
- **Незалежний перевіряльник замість довіри до розв'язувача.** Це дорожче (друга реалізація
  нутрієнтів, ціни, тверджень), зате ловить баги, які тест розв'язувача сам себе не побачить.
- **Спільне послаблення + альтернативи + «інший варіант».** Кожна пропозиція повертається лише
  після повторного розв'язку з перевіркою; eval додатково підставляє її в spec і проганяє сам.
  Минімальний конфлікт — один (deletion filter), не всі можливі.
- **Чесне `partial` / `unsupported` замість здогадів.** Краще сказати «шаблон не передбачає», ніж
  вигадати інгредієнт чи категорію.
- **Тести без мережі:** `FakeLLM`, сервіс `test` в ізольованій Docker-мережі.
- **Eval:** dev і test розділені; test писав субагент лише з умови; кеш відповідей моделі в git.

## Межі (чого сервіс не моделює)

- В'язкість, pH, смак, текстуру, стабільність, термін придатності, органолептику: лише межі доз і
  склад шаблону. «Щільна текстура» чи «зберігається 6 місяців» — `unsupported`.
- Втрати при термообробці (крім фіксованої для печива), біодоступність, якість білка (рахується
  кількість, не амінокислотний склад: желатин і насіння дають «білок» як і інші).
- Ціни — оцінки; нутрієнти — типові значення, не специфікації постачальника; еталони —
  усереднені, не вимірена вибірка. Це не висновок для маркування: перед тиражем потрібна
  лабораторія.
- 8 категорій, 68 інгредієнтів; одночасно одна рецептура (мінімум собівартості), без
  багатокритеріальної оптимізації й без «топ-N варіантів».
- Розбір тексту залежить від LLM: на фінальному test 2 з 52 ключових обмежень пропущено, 5 зайвих.
  Код перехоплює вигадані цитати й числа, але правильно прочитане «не те» слово — ні.

## Що далі

- Перезамір на новому наборі запитів і новому тест-субагенті — тепер, коли в базі є фундук, шпинат,
  какао; поточні `proof*.md` описують дані до цього.
- Реальні прайси постачальників замість оцінок; вимірені еталони категорій.
- Показувати кілька мінімальних конфліктів, а не один (слабке місце конфліктів у метриках).
- Кандидат із `docs/NOTES.md`: ліміт собівартості в «вікні округлення» (≈ 0,4 %) сьогодні дає 500
  `rounding_failed`, хоч LP здійсненний; має бути `infeasible` з послабленням до округленої ціни.
- MILP для мінімальних доз; натуральна ваніль; більше категорій.

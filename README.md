# Recipe Constraints

Технолог пише словами, який продукт хоче («полуничний йогурт без молока, білка не менше, ніж у
звичайного, собівартість до 45 грн/кг, і щоб можна було написати "зі зниженим вмістом цукру"»).
Сервіс повертає **рецептуру в грамах на 1 кг готового продукту** або чесно пояснює, чому такої немає
і що саме послабити. Ринок — Україна, тексти українською; твердження — Наказ МОЗ № 1145
(= додаток Регл. 1924/2006).

## Доказ коротко

Фінальний замір — один раз, живою моделлю, на 20 прихованих test-запитах, які писав окремий агент
лише з умови таски: **15 з 15 рецептур пройшли незалежну перевірку**, статус збігся в 16 з 20, усі
8 запропонованих послаблень підтвердились повторним розв'язком. Звіт з кожним запитом, рецептурою й
перевірками — [`docs/proof.md`](docs/proof.md). Відтворити без ключа й мережі:
`git checkout final-test-eval && make eval SPLIT=test && make proof`.

Метрики поточного коду поряд із фінальним заміром і всі команди відтворення — [`docs/proof_index.md`](docs/proof_index.md).

## Архітектура: модель розуміє, розв'язувач рахує, незалежний код перевіряє

```
текст запиту → LLM (Gemini; запасний Groq): ЛИШЕ структурування в ConstraintSpec
               з цитатою фрази-джерела + unparsed[] (що не зрозуміла)
            → код: валідація (вигадана цитата чи число → відкинуто), розгортання: шаблон продукту,
               еталон, твердження, алергени → лінійні обмеження
            → LP-розв'язувач (scipy HiGHS): мінімум собівартості, Σ = 1000 г
            → є рішення: округлення до 0,1 г → рецептура
              немає: еластичний LP → конфлікт + «що послабити» (кожна пропозиція перевірена
              повторним розв'язком)
            → НЕЗАЛЕЖНИЙ перевіряльник (app/verify.py: рахує з грамів і YAML, не з матриць
               розв'язувача): нутрієнти, ціна, алергени, твердження, дози, шаблон → checks[]
            → PostgreSQL: запит, spec, рецептура, checks, модель, версії (аудит)
```

Модель не рахує і не вигадує цифр: грами, нутрієнти, ціни, пороги — лише код і дані. **Рецептура
віддається, лише якщо незалежна перевірка пройшла всі checks.** Інакше відповідь — помилка
`verification_failed`: це баг, а не відповідь. Жодна фраза запиту не губиться мовчки: вона стає
обмеженням, потрапляє в `unparsed` (не зрозуміла) або в `unsupported` (зрозуміла, але не
підтримуємо). Якщо такі фрази є, статус ніколи не `feasible`, а `partial`.

Стек: Python 3.12, FastAPI, Pydantic v2, PostgreSQL 16 (asyncpg, SQL-міграції), scipy (HiGHS),
httpx, Docker Compose, pytest, ruff, GitHub Actions. Фронтенду немає — Swagger UI.

## Запуск

На хості потрібні Docker (Compose v2), `make` і `curl`.

```bash
cp .env.example .env      # вписати GEMINI_API_KEY (Google AI Studio, free tier, без картки)
make up                   # db + api: http://localhost:8020 (Swagger UI: /docs)
make health               # {"status":"ok","db":"ok","llm_provider":"gemini",...}
make test                 # ruff + 318 тестів: без мережі й ключів, окрема БД recipe_test
```

Ключ потрібен лише для `POST /formulate` (розбір тексту). Усе інше працює без ключа й без мережі:
`/formulate/structured`, `make test`, відтворення eval з кешу. Запасний провайдер — Groq
(`GROQ_API_KEY`, `LLM_FALLBACK_PROVIDER=groq`, модель `openai/gpt-oss-120b`). Порти: api `8020`,
db `127.0.0.1:5434`. `make down` зупиняє стек; дані лишаються в томі `pgdata`.

## Як перевірити своїм запитом

```bash
scripts/ask.sh "полуничний йогурт без молока, білка не менше, ніж у звичайного, до 45 грн/кг, зі зниженим вмістом цукру"
make ask Q="злаковий батончик з фундуком і какао, без арахісу, до 120 грн/кг"
scripts/ask.sh --json "пиріг з нутелою"        # сира JSON-відповідь
```

Потрібні `make up` і `GEMINI_API_KEY` у `.env`. Скрипт робить `POST /formulate` і друкує:
- статус;
- рецептуру таблицею, собівартість і нутрієнти на 100 г;
- перевірки ✅/❌;
- `unsupported` / `unparsed` з причинами;
- для нездійсненного запиту — конфлікт, мінімальні послаблення й рецептуру з послабленням.

Усі числа беруться з відповіді API. Кожен запит зберігається в БД: `run_id` є у виводі, відповідь
доступна через `GET /formulate/{id}`.

Приклад виводу (скорочено) — запит з умови, який **нездійсненний**:

```
Статус: ❌ infeasible — за цих вимог рецептури немає (див. «Конфлікт» і «Що послабити»)
Конфлікт (ці вимоги разом неможливі):
  • собівартість не більше 45 грн/кг  («собівартість до 45 грн/кг»)
  • без алергену milk: виключено Молоко пастеризоване 2,5 %, … («без молока»)
Щоб рецептура існувала, треба одночасно:
  • послабити: собівартість не більше 45 грн/кг → 52,9 грн/кг → рецептура 52.84 грн/кг
Інший варіант (не автоматично):
  • відмовитись від вимоги: без алергену milk … → рецептура 36.03 грн/кг
    ⚠️  вимогу щодо алергену/дієти не послаблюємо автоматично: рецептура міститиме виключене …
Рецептура зі спільним послабленням (relaxed_recipe):
  Соєвий напій 805.3 г, Полуниця 100 г, Цукор 85.8 г, Ізолят соєвого білка 8.8 г, Закваска DVS
  «без молочного» 0.1 г → 52.84 грн/кг; білок 3.2 г/100 г (еталон 3.2), цукри 9.45 ≤ 9.45
```

Той самий запит **з молоком** здійсненний за 36,03 грн/кг: молоко 2,5 % 831,06 г, полуниця 100 г,
цукор 50,4 г, закваска 10 г, ізолят сої 8,5 г, стевія 0,04 г; усі 23 правила шаблону пройшли.
«Пиріг з нутелою» дає `unsupported` з переліком 9 підтримуваних категорій.

## API

- `POST /formulate` — `{"request": "<текст>"}` → розбір LLM + рецептура.
- `POST /formulate/structured` — `{"spec": ConstraintSpec}` → те саме без LLM. Для тестів, eval і
  демо; у Swagger є готові приклади, ключ не потрібен.
- `GET /formulate/{id}` — збережена відповідь.
- `GET /ingredients`; `GET /templates` (із собівартістю базової рецептури й еталоном); `GET /health`.
- Помилки мають вигляд `{"error": {"code": "...", "message": "..."}}`:
  - `llm_bad_output` (502);
  - LLM недоступний, не налаштований або вичерпано ліміт (503);
  - `verification_failed`, `solver_error`, `template_infeasible`, `rounding_failed` (500) — це баги,
    а не відповіді. `rounding_failed` лишився лише на випадок, коли навіть мінімальне послаблення не
    дає зваженої рецептури; звичайне «вікно округлення» повертає `infeasible`, див. нижче.

`FormulateOut` містить такі поля:
- `status`: `feasible` | `partial` | `infeasible` | `unsupported`;
- `recipe`, `totals` (`cost_uah_per_kg`, `per_100g`, `ingredients` — скільки куплених інгредієнтів, `water`);
- `checks[]` (`id`, `kind` hard/soft, `requested`, `actual`, `pass`, `source_phrase`);
- `parsed` (spec, який зрозуміла модель), `unparsed`, `unsupported`;
- `conflicts`, `relaxations`, `alternatives`, `other_options`, `relaxed_recipe`, `other_recipe`
  (рецептура найдешевшого «іншого варіанту» — алерген чи дієта знято, з попередженням), `explanation`;
- `contradictions`, `assumptions`.

Деталі — `docs/SPEC.md` §1.

## Де сервіс помилявся і що виправлено

Фінальний замір у `docs/proof.md` не змінювався. Виправлення нижче видно в звіті поточного коду
(`docs/proof_head.md`).

- **Апельсиновий сік (t01).** Було: «апельсиновий сік» отримував по третині апельсинового соку,
  яблучного соку і яблучного пюре — так видно в `docs/proof.md`, і перевірка це пропускала. Зараз:
  названий сік — увесь сік (апельсиновий 1000 г). Окрема перевірка «назва відповідає складу» ловить
  підміну; суміш буває, лише коли в запиті названо кілька смаків.
- **Апельсиновий напій (t15).** Було: «апельсиновий» напій містив по 5 % апельсинового і яблучного
  соку. Зараз: названий смак — не менше мінімуму ролі й не менше половини ролі (апельсиновий 10 %, без
  яблучного).
- **«Без горіхів та мигдалю».** Було: у проміжній версії конкретний горіх поруч із загальним словом
  звужував виключення до одного мигдалю. Зараз: «горіхи / горіх / nuts» у фразі виключення завжди
  означає всі горіхи. «Без мигдалю» виключає лише мигдаль; арахіс — окрема категорія.
- **Вікно округлення.** Було: ліміт ціни між оптимумом LP і найдешевшою зваженою рецептурою давав
  500 `rounding_failed`. Зараз: `infeasible` з поясненням і перевіреним послабленням на
  0,01–0,05 грн/кг.
- **Печиво з водою.** Було: пісочне печиво мало до 152 г води на 1111 г тіста (≈ 14 %), бо вода
  дешева. Зараз: додана вода ≤ 5 % тіста, жиру в готовому ≥ 15 г/100 г, цукор у йогуртах ≤ 10 %.

Що лишилось як є (фінальний замір):
- Конфлікти. Розв'язувач називає **один** мінімальний конфлікт, а очікування в test часто перелічує
  ширший (recall 3 з 7).
- Розбір. «Протеїновий батончик» модель надобережно позначила `unsupported`.
- Відсутні інгредієнти. Двом запитам бракувало інгредієнтів (фундук, шпинат) — сервіс чесно вніс їх
  у `unsupported`; згодом їх додали в базу.
- Dev-запит d09 («смузі з високим вмістом білка, до 30 грн/кг») було помилково записано як
  нездійсненний. Маложирне смузі досягає «білок ≥ 20 % енергії» за 25,25 грн/кг, і рецептура проходить
  усі перевірки.

## Припущення

Питань до замовника не було: усе, що виглядало як розвилка, вирішено так і записано тут.

1. **Ринок — Україна, тексти українською.**
   - Порівняльні твердження («зі зниженим вмістом…») — щонайменше на 30 % менше за еталон (для солі —
     25 %); для цукрів ще й енергія ≤ еталону.
   - Абсолютні — пороги Наказу МОЗ № 1145 (`app/claims.py`).
   - Для рідин пороги задано на 100 мл, рецептуру рахуємо на 100 г: поріг ÷ густина шаблону
     (1,03–1,05 г/мл).
2. **«Звичайний» = еталон категорії** (`data/references.yaml`, з джерелом і поміткою «оцінка»).
   Немає еталона — порівняльна вимога `unsupported`, цифр не вигадуємо.
3. **Рецептура на 1000 г готового продукту**, без втрат при термообробці. Виняток — печиво: втрата
   вологи 10 % (сира маса — 1111,1 г) з перевіркою водного балансу.
4. **Технологічні межі — жорсткі** (`data/templates.yaml`, значення — припущення):
   - основа й закваска узгоджені (рослинна основа — лише рослинна закваска);
   - межі доз;
   - пісочне печиво: додана вода ≤ 5 %, жир ≥ 15 г/100 г;
   - йогурти: цукри й підсолоджувачі разом ≤ 10 %.

   Вимоги технолога — м'які: саме їх пропонуємо послабити. Алерген і дієта автоматично не
   послаблюються, лише як «інший варіант» з попередженням.
5. **Назва відповідає складу.** Названий смак («полуничний») має бути не менше мінімуму своєї ролі
   (йогурт — 10 % фрукта, смузі — 20 %, батончик — 10 % горіхів) і не менше половини ролі: полуниці
   не менше, ніж решти фруктів разом. Вимога «з X» без відсотка означає max(5 %, мінімум ролі).
6. **Не більше 6 інгредієнтів** (вимога технологів: кожен — окремий постачальник і аудит).
   Рахується все, що купується, включно з заквасками, сіллю й содою; вода з водопідготовки — ні.
   У відповіді — «N інгредієнтів + вода». Розв'язувач — MILP (scipy `milp`, HiGHS) з бінарним
   перемикачем на інгредієнт. Якщо рецептура неможлива саме через ліміт, конфлікт називає правило,
   а «Інший варіант (не автоматично)» дає рецептуру з 7 інгредієнтами з перевіркою. Незалежна
   перевірка рахує інгредієнти своїм кодом.
7. **Оптимізуємо собівартість.**
   - Ціль: собівартість + λ·Σ|x − базова рецептура|, де λ = 0,0001 грн/г — **лише тай-брейкер** між
     рівноцінними за ціною рецептурами. Переплата проти найдешевшої — не більше ≈ 0,2 грн/кг.
   - «Типовість» рецептури дає не λ, а технологічні межі шаблонів.
   - Округлення: до 0,1 г, нижче 1 г — до 0,01 г (стевія 0,04 г).
8. **9 категорій:** йогурт густий і питний, соковмісний напій (сік 10–49 %), нектар, сік 100 %,
   смузі, злаковий батончик, пісочне печиво, кетчуп. Мінімум соку в нектарі — 50 % (Директива
   2001/112/ЄС, додаток IV). Інша категорія — `unsupported` з переліком.
9. **Алергени.**
   - «Без X» виключає й те, що X містить (молоко → СЗМ, сироватковий білок, закваска, масло).
   - «Може містити» враховується як «містить».
   - «Без цукру», «без доданого цукру» і «зі зниженим вмістом цукру» — різні вимоги.
   - «З горіхами» — будь-який горіх шаблону.
   - Сертифіковані безглютенові вівсяні пластівці (≤ 20 мг/кг глютену, Регл. (ЄС) 828/2014) не
     декларуємо як злаки з глютеном; звичайні вівсяні — декларуємо.
10. **Дані — оцінки.** Нутрієнти — USDA FDC і типові специфікації, у конвенції ЄС (вуглеводи без
   клітковини; енергію звірено з Atwater при завантаженні). «Ваніль» — ароматизатор ванілін.
11. **LLM** лише структурує текст. Код відкидає вимоги з вигаданою цитатою чи числом, а непокриті
    слова перетворює на `unparsed`.

## Джерела цін

Усі ціни в `data/ingredients.yaml` — **оцінки в грн/кг на жовтень 2026, а не котирування**; у
кожного інгредієнта є `price_source` і `price_date`. Докладно — [`data/PRICES.md`](data/PRICES.md).

Три ціни підтверджено відкритими джерелами:
- цукор — 21,32 грн/кг;
- молоко-сировина — 16 грн/кг;
- соняшникова олія — ≈ 108 грн/кг.

Решта — оцінки відносно цих опор. Рецептура залежить передусім від **співвідношення** цін. Для
реального використання ціни замінюють прайсами постачальників у YAML.

## Рішення і компроміси

- **LP, а не перебір чи LLM.** Усі вимоги лінійні за грамами. HiGHS детермінований і дає сертифікат
  нездійсненності, а еластичний LP природно відповідає на «що послабити».
- **Незалежний перевіряльник.** Це друга реалізація нутрієнтів, ціни й тверджень: дорожче, зате
  ловить баги розв'язувача.
- **Кожне послаблення перевірене.** Його повторно розв'язують у сервісі, а eval ще раз підставляє його
  в spec і проганяє сам. Мінімальний конфлікт показуємо один, не всі.
- **Чесне `partial` / `unsupported` замість здогадів.**
- **Тести без мережі** (`FakeLLM`, ізольована Docker-мережа). Eval: dev і test розділені, відповіді
  моделі — у git.

## Межі

- Не моделюємо в'язкість, pH, смак, текстуру, термін придатності: це `unsupported`.
- Не моделюємо втрати при термообробці (крім печива) і якість білка.
- Нутрієнти й ціни — типові значення. Це не висновок для маркування: перед тиражем потрібна
  лабораторія.
- 9 категорій, 68 інгредієнтів; одна рецептура на запит (мінімум собівартості), без «топ-N».
- Розбір залежить від LLM: на фінальному test 2 з 52 ключових обмежень пропущено, 5 зайвих.

## Що далі

- **Новий чесний замір.** `docs/proof.md` описує код і дані на момент заміру; `docs/proof_head.md` —
  поточний код на тих самих 20 запитах, тож він уже не прихований. Потрібен новий набір test-запитів.
- Показувати кілька мінімальних конфліктів, а не один — найслабша метрика (конфлікти, recall 5 з 9
  на поточному коді).
- Реальні прайси постачальників і вимірені еталони замість оцінок.
- MILP для мінімальних доз; більше категорій.

## Структура

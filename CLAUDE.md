# Recipe Constraints — правила проєкту для Claude Code

Тестова таска: технолог пише словами, який продукт хоче («полуничний йогурт без молока,
білка не менше, ніж у звичайного, собівартість до 45 грн/кг, і щоб можна було написати
"зі зниженим вмістом цукру"»). Сервіс повертає рецептуру в грамах на 1 кг або пояснює,
чому такої немає і що послабити.

Обмеження: Python, FastAPI, PostgreSQL, Docker; лише безкоштовні сервіси без картки;
8 годин; свій код з попередніх тасок брати можна (`~/label-check`, `~/pet`); питань не
буде — усі припущення в README; ціни правдоподібні, з джерелом порядку цифр.
Що здати: репозиторій, що запускається з нуля за README; **доказ, що рецептури справді
відповідають запиту**; увечері PM дасть невідомі запити — сервіс має на них поводитись чесно.

Деталі (моделі даних, обмеження, розв'язувач, перевірка, eval) — `docs/SPEC.md`, читати лише
розділ, потрібний кроку; «чому так» — `docs/OVERVIEW.md`; кроки — `docs/steps/`; пам'ять між
кроками — `docs/NOTES.md`.

## Рішення і припущення

1. **Ринок — Україна**, тексти українською; твердження — Наказ МОЗ № 1145 (= додаток
   Регл. 1924/2006). Порівняльні («зі зниженим вмістом…») — ≥ 30 % менше за еталон, для
   цукрів ще й енергія ≤ еталону.
2. **«Звичайний» = еталон категорії** з `data/references.yaml` (з джерелом цифр). Немає
   еталона — порівняльна вимога `unsupported`, не вигадуємо.
3. **Рецептура на 1000 г готового продукту**, без втрат при термообробці (для печива —
   фіксований коефіцієнт втрати вологи з шаблону, явне припущення).
4. **Оптимізуємо собівартість** серед рецептур, що задовольняють усе; ціни — `data/ingredients.yaml`
   з `price_source` і датою.
5. **Лише категорії з `data/templates.yaml`** (6–8 шаблонів). Інша категорія → чесне
   `unsupported` з переліком підтримуваних.
6. LLM: текстова модель Gemini (free tier) + запасний Groq `openai/gpt-oss-120b`, як у `pet`.
7. Фронтенду немає — Swagger UI.

## Архітектура: модель розуміє, розв'язувач рахує, незалежний код перевіряє

```
текст запиту → LLM: ЛИШЕ структурування в ConstraintSpec (+ unparsed[] — що не зрозуміла)
            → код: розгортання (шаблон продукту, еталон, твердження, алергени) → лінійні обмеження
            → LP-розв'язувач (scipy HiGHS): мінімум собівартості, сума = 1000 г
            → є рішення: округлення до 0,1 г → рецептура
              немає: еластичний LP + «що послабити» (кожна альтернатива перевірена повторним розв'язком)
            → НЕЗАЛЕЖНИЙ перевіряльник (інший код, не матриці розв'язувача): нутрієнти, ціна,
              алергени, твердження, дози, шаблон → checks[] pass/fail
            → PostgreSQL: запит, spec, рецептура, checks, модель, версії (аудит)
```

## Жорсткі правила (не порушувати)

- **Модель не рахує і не вигадує цифр.** Лише переносить вимоги з тексту в ConstraintSpec,
  з цитатою фрази-джерела. Грами, нутрієнти, ціни, пороги — тільки код і дані.
- **Жодна фраза запиту не губиться мовчки.** Кожна — або обмеження, або `unparsed`
  (не зрозуміла), або `unsupported` (зрозуміла, але не підтримуємо). Статус відповіді з
  `unsupported` ніколи не `feasible` без застереження: `partial`.
- **Рецептура віддається, лише якщо незалежна перевірка пройшла всі checks.** Інакше —
  помилка `verification_failed` з деталями (це баг, а не відповідь).
- **«Неможливо» завжди з поясненням**: які вимоги конфліктують і мінімальні послаблення;
  кожна запропонована альтернатива перевірена повторним розв'язком.
- **Технологія — жорсткі обмеження** (основа продукту, межі доз, характерний інгредієнт),
  вимоги технолога — м'які (саме їх пропонуємо послабити). Алерген-виключення не
  послаблюється автоматично — лише пропонується як «інший варіант» з попередженням.
- **Дані з джерелами.** Кожен інгредієнт: нутрієнти (джерело), ціна (джерело + дата),
  алергени. Ціни — оцінки, і README так і каже.
- **Тести без мережі й живого LLM** (`FakeLLM`; сервіс test в ізольованій мережі, як у label-check).
- **Eval чесний:** dev/test; test-запити пише субагент лише з умови таски (не бачить
  шаблонів і даних); фінальний замір test — один раз.
- **Помилки:** `{"error": {"code": "...", "message": "..."}}`. Міграції нумеровані,
  застосовані не редагуються. Секрети лише в `.env`.
- **Один крок плану = один коміт**, наступні кроки наперед не робимо.

## Автономний режим (як виконувати крок)

Людина пише «Виконай крок <X>». Тоді:
1. Прочитай `docs/steps/<X>.md` і розділи SPEC/NOTES, на які він посилається, — більше нічого
   без потреби (з `~/label-check`, `~/pet` — лише названі файли).
2. Зроби крок. Ворота з файлу кроку запускаєш **сам**. Червоне — виправ; після 3 невдалих
   спроб на тому самому — зупинись і опиши проблему.
3. Самоперевірка за `docs/steps/REVIEW.md`: критичне й важливе виправ (з тестом), ворота
   ще раз; дрібниці — у звіт.
4. Онови «Статус кроків» і `docs/NOTES.md`, закоміть з повідомленням із файлу кроку, `git push`.
5. Звіт ≤ 15 рядків: що зроблено; ворота; що знайшла самоперевірка; відкриті питання;
   наступний крок.

**Зупинись і спитай людину**, якщо: рішення поза планом (архітектура, схема БД, правило з
CLAUDE.md); ворота червоні після 3 спроб; живих викликів LLM більше за бюджет кроку; ⏸.
**Ніколи:** `--no-verify`, `push --force`, редагувати застосовані міграції, відкривати
`eval/requests/test/` в основному контексті до B5 (лише субагент і раннер), доналаштовувати
після фінального заміру на test.

## Стек

Python 3.12, `uv` (версії `==`), FastAPI, Pydantic v2, asyncpg + ручний SQL, PostgreSQL 16
(`postgres:16.15-bookworm`), **scipy (linprog, HiGHS)** для LP, httpx для LLM, pytest, ruff,
Docker (двостадійний), Compose, GitHub Actions. Порти: api **8020**, db **127.0.0.1:5434**
(8010/5433 — label-check, 8000/5432 — pet).

## Структура

```
app/  main, config, db, logs, errors (з label-check)
      schemas.py        ConstraintSpec, Recipe, Check, FormulateOut
      data.py           завантаження і валідація data/*.yaml
      expand.py         ConstraintSpec → лінійні обмеження (шаблон, еталон, твердження, алергени)
      solver.py         LP, округлення, еластичний LP, альтернативи
      verify.py         незалежна перевірка → checks[]
      claims.py, allergens.py   адаптовано з label-check
      llm/              base, gemini, groq, fallback, fake (з pet), prompt.py
      parse.py          текст → ConstraintSpec (кеш, валідація, unparsed)
      formulate.py      run_formulate(text|spec) — спільне для API і eval
      routers/          formulate, ingredients, templates, health
data/ ingredients.yaml, references.yaml, templates.yaml, PRICES.md (джерела цін)
eval/ requests/{dev,test}/*.yaml, run.py, metrics.py, reports/, cache/
docs/ OVERVIEW, SPEC, NOTES, steps/, proof.md (генерується)
```
